19//! `std` facade for the `tf_tree` transform engine.
20//!
21//! Re-exports the [`tf_tree_core`] engine and adds the ergonomic, allocating
22//! conveniences that do not belong in the `no_std` core: the [`TreeBuilder`] and
23//! the [`Tree`] that owns a `HeapArena`, the plan-cached [`Tree::lookup`], and
24//! [`Described`] — a `Display` wrapper that resolves error ids to frame names by
25//! consulting the arena (the error type itself stays `Copy` and `no_std`).
26//!
27//! Most users depend on this crate, not on `tf_tree_core` directly.
28//!
29//! ```
30//! use tf_tree::{TreeBuilder, InterpPolicy, Stamp, Iso3};
31//!
32//! // Topology is declared on the builder; `build()` sizes the arena from exactly
33//! // these edges (static edges reserve no ring slots).
34//! let tree = TreeBuilder::new()
35//!     .static_edge("map", "odom", &Iso3::IDENTITY)
36//!     .build()
37//!     .expect("layout");
38//!
39//! // map -> odom is a static identity, so the lookup is identity at any time.
40//! // A typed binding pins the default `SystemDomain` (method-call inference does
41//! // not apply a type parameter's default, so annotate the stamp once).
42//! let now: Stamp = Stamp::from_nanos(0);
43//! let t = tree.lookup("map", "odom", now).unwrap();
44//! assert_eq!(t, Iso3::IDENTITY);
45//! # let _ = InterpPolicy::ScLerp;
46//! ```
47//!
48//! # Minimum supported Rust version
49//!
50//! **1.87**. It is declared in `[workspace.package] rust-version` and repeated
51//! here because a manifest is not somewhere a user reads: the person deciding
52//! whether they can adopt this crate opens the docs, and `cargo` refusing to
53//! build is a worse way to find out. `just msrv` builds `--locked` on exactly
54//! that toolchain and fails if this line, `README.md`, `SUPPORT.md` or any
55//! hand-written `rust-version` disagrees with the manifest.
56//!
57//! An MSRV bump is a minor-version bump pre-1.0 and a breaking change after —
58//! `SUPPORT.md` is the policy, including why each of the two steps so far was
59//! forced by a dependency rather than chosen.
60//!
61//! # Two stability tiers
62//!
63//! Everything at this crate's root is the **stable** surface: at a published tag
64//! each `pub` item is a semver promise. The `tf_tree::unstable` module — behind
65//! the default-off `unstable` feature, so it is absent from these docs unless
66//! that feature is on — is not, and enabling the feature is the waiver
67//! (`docs/API.md` §2.6). It mirrors the C ABI's `tf_tree.h` /
68//! `tf_tree_unstable.h` split, which is the same promise spelled as two headers.
69//!
70//! What lives there is what the *arena layout* shapes, because that layout is
71//! scheduled to change (`docs/PHASE5.md` §1). If you are reading transforms, you
72//! will never need it.
73//!
74//! **Gating a door is not the same as removing a room.** The question the gated
75//! `Tree::arena_view` used to be the only Rust answer to — *what is in this
76//! tree?* — is answered on the stable tier by [`Tree::frames`] and
77//! [`Tree::edges`], which mirror Python's `tree.frames()` / `tree.edges()`
78//! (`docs/API.md` §3.2). Names only: the statistics half is `docs/PHASE5.md`
79//! §4.2's and is held back on every surface until §3's counting pass. Enabling
80//! `unstable` buys the arena-shaped *spelling* of that answer — record fields,
81//! capacities, counters — not the answer itself.
82//!
83//! The three items that moved do not answer at the crate root any more, and this
84//! is what pins that — **but only when the feature is on**, and where that holds
85//! moved in 0.0.1. It used to be every `cargo test` here, because the crate
86//! dev-depended on itself to enable `unstable`; that line did not survive
87//! `cargo package` and is gone. Today the assertion means "moved to
88//! `tf_tree::unstable`" under `cargo test --doc --workspace`, which unifies the
89//! feature in from the four consumers that declare it, and degrades to the
90//! weaker "absent from the crate root" under a bare `-p tf_tree`. Both readings
91//! are true; `just test` runs the strong one:
92//!
93//! ```compile_fail,E0432
94//! use tf_tree::ArenaView;
95//! ```
96//! ```compile_fail,E0432
97//! use tf_tree::EdgeKind;
98//! ```
99//! ```compile_fail,E0432
100//! use tf_tree::EdgeMeta;
101//! ```
102//!
103//! Three blocks and not one `use tf_tree::{ArenaView, EdgeKind, EdgeMeta};`,
104//! because a single block passes as soon as *any* one of the three is absent —
105//! it would go on passing after a refactor put two of them back.
106//!
107//! `E0432` and not a bare `compile_fail`: an unpinned one passes when the
108//! snippet fails for *any* reason, and stable rustdoc ignores the code, so
109//! `just test-doc-error-codes` is this line's real gate (`justfile`).
110//!
111//! ## What the pre-tag audit left alone, and why
112//!
113//! The sweep behind the split asked `docs/API.md` §7 of every `pub` item here.
114//! Three moved; the rest stay, and two answers are worth recording because they
115//! look like omissions:
116//!
117//! * **[`EdgeWriter`] still carries a lifetime**, which §2.1 calls a violation.
118//!   It is a *known* one and it is not the bug: [`OwnedWriter`] is the storable
119//!   shape, and a scoped claim whose scope the borrow checker enforces is better
120//!   when it fits. §2.1 says so in terms.
121//! * **[`Described`]'s two fields became private.** They promised that the
122//!   `Display` wrapper is exactly `(error, tree)` forever, for no caller — the
123//!   only construction site in the workspace is [`Tree::describe`].
124//!
125//! `tf_tree_core`'s crate docs carry the rule the audit applied to
126//! `#[non_exhaustive]`, and the per-type arguments sit on the types.
127//!
128//! # `no_std` / `std` split
129//!
130//! Everything arena-generic — [`Plan`], [`Step`], [`Guard`], [`Stamp`],
131//! [`Domain`], [`Query`], the compile/evaluate engine — lives in the `no_std`
132//! [`tf_tree_core`]. This crate adds only what needs `std`: the concrete [`Tree`]
133//! owning a heap arena, the per-thread plan cache behind [`Tree::lookup`]
134//! (`thread_local!`), and [`Described`]'s `Display`.
135//!
136//! # [`Tree`] is not `Clone`, and `Arc<Tree>` is the embedding idiom
137//!
138//! [`Tree`] is `Send + Sync`, so a shared reference is all a reader needs — but
139//! it is deliberately not `Clone`, and the reason is that a `Tree` is not just a
140//! handle. It owns its arena backing *and* holds a registered slot in the
141//! arena's participant table — a fixed-size table (`DEFAULT_MAX_PARTICIPANTS`,
142//! 64) sized when the arena is created, not an unbounded pool. A derived
143//! `Clone` would have to pick one of two wrong answers: register a second slot,
144//! and burn a scarce resource every time somebody passed a tree by value; or
145//! share the first one, and report two participants as one to the reaper that
146//! decides whether a slot's owner is still alive.
147//!
148//! So share it with an `Arc`:
149//!
150//! ```
151//! use std::sync::Arc;
152//! use tf_tree::{Iso3, Stamp, TreeBuilder};
153//!
154//! let tree = Arc::new(
155//!     TreeBuilder::new()
156//!         .static_edge("map", "odom", &Iso3::IDENTITY)
157//!         .build()
158//!         .expect("layout"),
159//! );
160//! let reader = Arc::clone(&tree);
161//! let joined = std::thread::spawn(move || {
162//!     let now: Stamp = Stamp::from_nanos(0);
163//!     reader.lookup("map", "odom", now)
164//! })
165//! .join()
166//! .expect("reader thread");
167//! assert_eq!(joined.unwrap(), Iso3::IDENTITY);
168//! ```
169//!
170//! This is not new advice, which is the point of writing it down: `tests/tsan.rs`
171//! shares a tree between threads this way, `tf_tree_c` hands out
172//! `Arc<TreeShare>` (a one-field wrapper around a `Tree`, so the refcount is on
173//! the wrapper rather than on the `Tree` itself), and PyO3's `Py<PyTree>` is the
174//! same refcount spelled in CPython's allocator. Three surfaces arrived here
175//! independently and none of them said so where an embedder would look
176//! (`docs/API.md` §2.2).
177//!
178//! # Set `lto = "thin"` and `codegen-units = 1` in your release profile
179//!
180//! ```toml
181//! [profile.release]
182//! lto = "thin"
183//! codegen-units = 1
184//! ```
185//!
186//! **This is worth about 25% of a depth-3 lookup, and it is not cargo-cult
187//! advice — it is a property of where this engine's code lives.** [`Plan::at`]
188//! sits across a crate boundary from every consumer, and it and the fold beneath
189//! it live one crate further down still, in `tf_tree_core`. Five functions on
190//! the evaluate path carry `#[inline]` for exactly that reason (`Plan::at`, the
191//! scalar fold, and the three [`Guard`] sampling entry points), but what an
192//! attribute buys depends on **your** profile, not on ours: cargo's
193//! `--release` defaults are `lto = false, codegen-units = 16`, and this
194//! workspace's are not, so every latency number this project publishes is taken
195//! under whole-program optimisation and your node's is not.
196//!
197//! Measured rather than asserted, because the last claim made here about this
198//! mechanism was wrong in a way only a probe could show. One program — a
199//! depth-3 `map <- imu_link` lookup, `LerpSlerp`, off-grid stamps so the
200//! interpolation runs, one lookup per non-inlinable call — built twice and
201//! pinned to one core, nine rounds each, three consecutive runs:
202//!
203//! | downstream profile | ns/lookup |
204//! | --- | --- |
205//! | `lto = false`, `codegen-units = 16` (cargo's `--release` default) | 240 |
206//! | `lto = "thin"`, `codegen-units = 1` | 193–195 |
207//!
208//! On a 4-physical-core AMD EPYC-Milan VM under moderate load, 2026-08-02, so
209//! read it as "about a quarter", not as three digits — the ratio itself moved
210//! between 1.19× and 1.24× across those runs.
211//!
212//! **The same runs also say *why*, which is the part that makes this advice
213//! rather than folklore.** They time a second, identical body compiled *inside*
214//! `tf_tree_core`, and compare it against the one outside:
215//!
216//! | downstream profile | from outside the engine | from inside it |
217//! | --- | --- | --- |
218//! | `lto = false`, `codegen-units = 16` | 240 ns | 191 ns |
219//! | `lto = "thin"`, `codegen-units = 1` | 193 ns | 194 ns |
220//!
221//! At cargo's defaults the crate boundary costs about a quarter of the lookup;
222//! with thin LTO it costs nothing measurable, because the boundary is gone at
223//! link time. `just embed-cost` in this repository re-measures both, and
224//! `docs/PHASE5.md` §9.2 makes the second one a standing, gated benchmark row so
225//! the next change to those attributes moves a number somebody sees.
226//!
227//! The cost of taking this advice is build time: thin LTO adds a link-time
228//! optimisation pass, and `codegen-units = 1` gives up intra-crate build
229//! parallelism. Both are compile-time costs and neither changes what the shipped
230//! binary computes. How the 25% splits between the two settings has **not** been
231//! measured here, so if your release builds are slow enough that you want to
232//! take only one of them, measure your own case rather than trusting a guess
233//! from this paragraph.
